# Open-source Release Checklist

Use this before making the repository public.

This checklist intentionally distinguishes documentation readiness from runtime verification.

## 1. Licensing — blocking

- [ ] Choose an OSI-compatible license.
- [ ] Add the exact `LICENSE` text at repository root.
- [ ] Replace `UNLICENSED` in package manifests with the selected SPDX identifier where appropriate.
- [ ] Confirm third-party dependency licenses are compatible.
- [ ] Decide whether project name/logo/trademarks need a separate trademark policy.

See [LICENSING.md](./LICENSING.md).

**Current state:** no license selected. Do not call the repository an open-source licensed release yet.

## 2. Reproducible dependency install — blocking

- [ ] Run clean installs for `server/` and `web/`.
- [ ] Generate and commit deterministic lockfiles.
- [ ] Verify the lockfiles are generated by the package manager/version you intend to support.
- [ ] Run dependency audit/scanning and triage findings.

## 3. Build / tests — blocking

Run and record actual results:

```bash
npm run check
npm run typecheck:web
npm run build:web
npm run build:server
npm run test:server
```

- [ ] Add/enable CI to run the same checks on pull requests.
- [ ] Do not mark tests as passed when a command was not executed.

## 4. Database — blocking

Against a disposable Supabase project:

- [ ] apply `001_initial_schema.sql` from clean state;
- [ ] create a user and confirm `app_users` trigger;
- [ ] claim trial once successfully;
- [ ] verify a second claim fails;
- [ ] verify trial expiry behavior;
- [ ] verify sensitive tables are not directly readable by `anon/authenticated`;
- [ ] verify service-role backend operations work.

## 5. Stitch runtime — blocking for a Stitch release claim

With a non-production test key:

- [ ] test connection;
- [ ] save connection;
- [ ] run `tools/list`;
- [ ] execute at least one real discovered tool;
- [ ] test invalid key behavior;
- [ ] test upstream error/timeout behavior;
- [ ] confirm logs do not contain the API key.

## 6. GPT Action smoke test

- [ ] deploy Gateway on public HTTPS;
- [ ] set correct `GATEWAY_PUBLIC_BASE_URL`;
- [ ] download the generated GPT kit;
- [ ] import `openapi.yaml` in GPT Builder;
- [ ] configure Gateway Bearer token;
- [ ] upload Knowledge / add Instructions;
- [ ] run `getGatewayProfile`;
- [ ] run service/tool discovery;
- [ ] execute a Stitch tool;
- [ ] verify expired/no Open ID does not execute MCP.

## 7. Security

- [ ] production secrets are absent from Git history;
- [ ] `.env` is ignored;
- [ ] Authorization headers are redacted at proxy/logging layer;
- [ ] TLS is mandatory;
- [ ] CORS contains production origins only;
- [ ] edge abuse/rate protection is configured;
- [ ] `SUPABASE_SERVICE_ROLE_KEY` is server-only;
- [ ] encryption key is backed up securely;
- [ ] private vulnerability reporting is enabled;
- [ ] `SECURITY.md` contact workflow is tested.

## 8. Documentation

- [ ] README screenshots/branding reflect the real deployed app, if added;
- [ ] all public URLs are real;
- [ ] no placeholder email/domain is presented as a real contact;
- [ ] Project Status matches source;
- [ ] API Reference matches controllers;
- [ ] Self-hosting instructions work from a clean machine;
- [ ] validation report is updated for the release commit;
- [ ] release notes/changelog are updated.

## 9. Repository settings

Recommended GitHub settings:

- [ ] default branch protection;
- [ ] require CI before merge;
- [ ] squash/rebase policy documented;
- [ ] Issues enabled;
- [ ] Discussions enabled if you want community support there;
- [ ] private vulnerability reporting enabled;
- [ ] Dependabot/Renovate or equivalent configured;
- [ ] secret scanning enabled where available;
- [ ] repository topics/description set.

## 10. Community health

- [ ] `CONTRIBUTING.md`;
- [ ] `CODE_OF_CONDUCT.md`;
- [ ] `SECURITY.md`;
- [ ] `SUPPORT.md`;
- [ ] issue templates;
- [ ] pull request template;
- [ ] changelog/release notes.

## 11. Commercial boundary

Before public launch, document what self-hosting receives versus your hosted commercial service.

Avoid relying on obscurity for entitlement security: an open-source operator controls their own deployment/database and can change membership rules in their fork.

Your hosted product's commercial Open ID is enforced by **your hosted Gateway instance**, not by a claim that self-hosted source cannot be modified.
